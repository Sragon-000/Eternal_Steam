# 방벽·건물 피격·적 공격 적용 결과

> **2026-09-25 현재 상태:** 방벽 연속 설치는 두 클릭 직선 예약으로 확장되었다. StartRegionSandbox에서 메인 기지 파괴는 영구 패배이며 백업 이어하기도 차단한다. 아래 개별 기지 영역 상실/대기는 일반·서브 기지 처리 및 이전 검증 범위다. [최신 문서 인덱스](README.md). 아래 본문과 검증 수치는 당시 기록을 보존한다.

2026-09-17. 원본 프로젝트의 `StartRegionSandbox`와 `OpenWorldSandbox`에 적용했다. 게임 빌드와 새 프로젝트 생성은 하지 않았다.

## 사용과 검증값

수정 → **설치 분류의 방벽** → 격자 클릭 → 확정. 방벽은 2×2m, 1셀이고 지면/토대 위에 설치할 수 있다. 기지 범위 밖에서도 적을 막는다. 수정 상태에서 기존 건물을 클릭하면 회수 예정이며, 취소 시 유지하고 확정 시 제거한다.

| 항목 | 설정 |
|---|---|
| 방벽 / 방어 건물 | 체력 100 |
| 일반 건물 / 전초 | 체력 50 |
| 넥서스 | 체력 1,000 |
| 토대 | 피격·차단 대상 제외, 위 건물 파괴 후 유지 |
| 적 공격 | **피해 1 고정**, 간격 1초, 외곽으로부터 XZ 거리 1m |
| 대상 탐색 | 반경 10m, 적별 위상을 분산한 0.25초 주기 |

체력은 각 건물의 `HealthModuleDefinition`, 간격·거리·탐색 주기는 `Content/Buildings/StartRegion/EnemyCombat.asset`에 있다. 두 오픈월드 씬이 이 검증 설정을 참조한다. 실행 객체가 수치를 복사하므로 실행 중 공유 에셋 수정은 즉시 반영하지 않는다. 피해는 `EnemyBuildingCombat.Damage` 상수다.

적은 접근하는 동안 피해를 주지 않으며 공격 거리 진입 뒤 1초를 기다린다. 넥서스에 도달해도 소멸하지 않는다. 지상 적은 주변 방어 건물을 우선하고, 이동 구간 앞의 방벽/일반 건물부터 공격한다. 공중 적은 방벽을 무시하고 방어 → 일반 → 넥서스 순으로 선택한다. 같은 우선순위에서는 건물 외곽까지의 XZ 거리, 동거리에서는 월드 표적 등록 ID 순이다. 유효한 공격 대상을 유지하며 장애물 파괴 후 다시 탐색한다. 기절은 이동·공격 중단, 냉각은 이동만 지연한다.

## 모듈 경계

- `BuildingCombatDefinition`: UI 분류와 별개인 넥서스/방어/일반/방벽 역할과 지상 차단 여부. 체력 기능이 없는 조합은 구성 오류로 검출한다.
- `BuildingTargetRegistry` / `IBuildingTargetQuery`: 월드 전체의 고유 핸들, 8m 공간 버킷, 실제 격자 회전을 반영한 점유 사각형. 가까운 버킷과 이동 구간만 검사한다. 넥서스 목록은 별도로 관리한다. 토대마다 중복되는 로컬 건물 ID를 표적 식별에 사용하지 않는다.
- `EnemyBuildingCombat`: 슬롯별 세대·목표 핸들·타이머 배열. 탐색/접근/이동 차단/공격을 담당하며, 적마다 GameObject를 만들지 않는다. 피격 직전에 표적 생존과 사거리, 지상 장애물을 확인한다.
- `HordeEnemyWorld`: 이동 구간 제한 계약과 도착 정책만 추가. 오픈월드는 Remain, 기존 데모는 기본 Remove를 사용한다.
- `OpenWorldContent.Factory`: 활성화된 건물만 표적에 등록. 파괴·회수 시 기존 BuildingWorld가 점유/외형을 제거하고 Factory가 표적/영역 등록을 해제한다. 가동 범위 밖 건물도 표적과 장애물로 남는다.
- `BuildingHitView`: 피격 때 0.15초 외곽선 표시. 선택 정보에 이름과 현재/최대 체력 표시. 상시 체력바는 없다.

넥서스 파괴 시 해당 기지의 영역만 상실한다. 다른 기지가 살아 있으면 새 목적지를 찾는다. 모두 없어지면 기존 소환 요청 수량은 보류하며, 적은 주변 공격 가능한 건물을 처리한 뒤 대기한다. 건물 소속을 다른 기지로 자동 이동하거나 새 결과 화면을 띄우지 않는다.

`Tools/ApplyBuildingCombat.cs`는 두 카탈로그의 기존 건물, 방벽 에셋/모델, 기존 4종 포탑 프리팹, 두 씬의 설정을 Editor API로 구성하는 재현 도구다. 실행 전 씬을 저장하고 Play를 종료해야 한다. `MeetingConstructionSetup` 재실행 시에도 전초의 체력·전투 역할이 사라지지 않게 했다.

검증 도구는 다음 형식으로 실행한다. 도구의 중첩 `result.success`와 반환값을 확인해야 한다.

```sh
unity command run_script --file Tools/VerifyBuildingCombat.cs --entry VerifyBuildingCombat.Main --project-path /Users/limseth/Projects/Eternal_Steam/Eternal_Steam --format json
```

Integration/Pause/입력 검사는 비어 있는 StartRegionSandbox의 Play 모드에서 실행한다. 검증 후 생성물·예약·적을 정리하며 씬 재시작 후에도 다시 통과했다. 처음 Pause 검사에서 HUD를 Sandbox와 같은 오브젝트로 가정한 검사 코드 오류는 실제 별도 HUD를 조회하도록 수정하고 재검증했다.

## CPU·GC 측정

`Tools/BenchmarkBuildingCombat.cs`: Run1=4천, Run2=1만, Run3=10만. 각각 **동일 배치 3회**, 30프레임 예열 후 60프레임, dt=1/60. 101개 정적 건물, 지상/공중 절반, 적 간 초기 격자 간격 0.75m. 측정은 대상 탐색/상태 + 이동/충돌 + 공격이다.

**평탄한 지형의 CPU 전투 코어 측정**이며 TWC 지형 검사, 실제 Terrain 높이 샘플링, 렌더링, 포탑의 반격, UI, 생성/파괴의 일회성 할당은 포함하지 않는다. 전체 게임 프레임 시간이나 실제 플레이 FPS로 해석하면 안 된다. 최초 긴 일괄 호출은 CLI 30초 제한을 넘어서 규모별로 분리했다. 반복 회전 계산은 건물 생성 시 축을 캐시하는 방식으로 줄였다.

| 동시 적 | 3회 중앙값(ms) | 3회 p95(ms) | 측정 루프 GC.Alloc |
|---:|---|---|---|
| 4,000 | 1.66 / 1.66 / 1.66 | 1.84 / 1.70 / 1.71 | 매회 0 이벤트 |
| 10,000 | 4.05 / 4.10 / 4.10 | 4.21 / 4.39 / 4.29 | 매회 0 이벤트 |
| 100,000 | 38.38 / 37.63 / 37.68 | 39.12 / 38.92 / 38.68 | 매회 0 이벤트 |

Unity ProfilerRecorder의 GC.Alloc을 현재 스레드에 제한해 측정했다. 각 호출에서 16KB 배열 할당 양성 대조군이 1개 이벤트로 검출되는 것을 확인했다. GC0 수집은 전부 0회였다. 이 Editor에서 `GC.GetAllocatedBytesForCurrentThread()`는 양성 대조군에도 0을 반환해 사용하지 않았다. 원시 구간별 측정치는 `Docs/Measurements/building-combat-*.txt`에 보관했다.

10만 적은 코어 처리만 약 38ms이므로 **60fps 충족 상태가 아니다**. 렌더링·실제 지형을 포함한 장시간 프레임 측정과 추가 최적화가 후속으로 필요하다. 이번 측정에서 상시 할당이나 적 전체×건물 전체 탐색은 추가하지 않았다. 이전 기능과 다른 처리 범위이므로 과거 프레임 수치와 10% 회귀 여부를 직접 비교하지 않는다.

지형 우회 길찾기, 방벽 자동 연결·드래그, 낮/밤·기지별 라운드·새 저장, 전력·에너지는 이번 범위에서 구현하지 않았다.
