# 기차·노선 예약 수정 적용 결과

> 후속 현재 상태: [이동 방어·통합 결과](기차_노선_이동방어_통합결과.md). 아래는 해당 단계 당시 기록이며 남은 작업은 후속 결과를 우선한다.

2026-09-28. 사용자 “다음작업 진행” 요청에 따라 P5 운행 중 노선 예약 수정을 적용했다. [1차 실행 검증](../../Validation/2026-09-28-railway-live-play.md)에 이어 실제 Unity에서 **프로젝트 EditMode 115/115** 및 예약 수정 Play 검증을 통과했다. 이동 방어(P6)와 전체 수동 입력 인수 완료를 뜻하지 않는다.

## 실제 동작

- 노선 상세의 **노선 편집**으로 운행 중에도 초안을 연다. 초안은 실제 운행 경로를 바꾸지 않는다.
- **순환 검증 → 노선 확정** 시 역에 정지한 기차는 즉시 수정한다. 이동·정차 서비스·연료 대기 중이면 예약 변경으로 저장한다.
- 운행 중 예약에서는 현재 적용 노선의 **첫 번째 역**을 유지한다. 새 예약 확정은 이전 예약을 교체하며 잘못된 새 초안은 이전 예약을 그대로 남긴다.
- 기존 노선의 마지막 역에서 첫 역으로 돌아오는 도착 경계에 재검증한다. 최초 출발 직전 첫 역에 머무르는 경우에는 다음 순환 복귀를 기다린다.
- 기차 ID·화물 종류·적재 화물·잔여 연료를 보존한다. 유지되는 역의 적재/하역 설정은 보존하고 새로 추가된 역은 0/0으로 시작한다. 적용 후 첫 역 방문 처리는 한 번만 수행한다.
- 중지 요청이 첫 역 도착과 겹치면 예약을 적용한 뒤 해당 역에 **정지**한다. 예약 때문에 자동 재출발하지 않는다.
- 상세/목록에서 예약 상태를 표시하고 **예약 변경 취소** 버튼으로 미적용 예약을 폐기한다. 초안 취소/패널 닫기는 확정된 예약을 취소하지 않는다.

## 재검증·실패 정책

다음은 기존 계획의 권고를 이번 구현에서 구체화한 기본 동작이며 별도의 원문 명시나 새로운 사용자 승인으로 표기하지 않는다.

| 경계 | 처리 |
|---|---|
| 편집 중 실제 노선 버전 변경 | 초안을 확정하지 않고 다시 열도록 안내 |
| 예약만 있는 새 선로 | 미리 독점하지 않음. 다른 노선이 먼저 확보할 수 있음 |
| 첫 역에서 선로·역·포트·점유 또는 저장된 경로가 달라짐 | 예약 실패로 표시, 기존 노선과 기차 유지. 자동으로 다른 경로를 찾지 않음 |
| 예약 실패 후 | 자동 재시도하지 않음. 사용자가 예약을 수정해 다시 확정하거나 취소 |
| 기존 운행 경로 자체도 무효 | 기존 오류 정지 규칙 사용. 예약으로 기차를 다른 위치에 옮기지 않음 |
| 역 수 감소로 연료가 새 용량을 초과 | 예약 확정과 실제 적용 양쪽에서 거부. 석탄 삭제·자동 환급 없음 |
| 예약 후 정지 상태에서 새 수정 확정 | 현재 정차 역을 유지하는 즉시 수정으로 기존 예약을 대체 |

경로 검증과 확보 가능 여부 확인을 모두 마친 후 선로 배정을 교체한다. 예약본 때문에 현재 선로 잠금이 풀리지 않는다. 기준 버전, 예약 역·경로, 실패 상태와 사유는 기존 v2 저장에 선택 필드로 함께 보관한다. 예약 필드가 없는 이전 v2 저장은 예약 없음으로 읽는다. 미확정 UI 초안은 계속 저장을 차단하지만 확정된 예약은 저장할 수 있다.

- `Tests/OpenWorld/Runtime/RailwayHud.cs`: 운행 중 편집, 기준 버전 확인, 예약 표시·취소.

- `Tests/EditMode/RailwayTests.cs`, `Tools/VerifyRailwayRevisionPlay.cs`: 경계·회귀·실제 실행 검증.

## 검증 결과

[Unity 원시 결과](../../Validation/2026-09-28-railway-p5-tests.json): **115/115 통과**, 실패/스킵 0. 철도 관련 26개를 포함한다.

이번에 추가한 11개 사례는 예약 지연 적용, 예약 저장·취소·오래된 초안 거부, 중지 우선, 예약 경로 변경 시 기존 운행 보존, 첫 역 변경/손상된 예약 버전 거부, 이동 구간 오류 복구, 3·4역 및 4개 배치 방향 순환, 다른 노선의 선로 선점 충돌이다. 선점 사례에서는 예약한 선로에 다른 노선을 실제 확정한 뒤 첫 역에서 예약 실패와 기존 노선 유지까지 검사했다.

실제 `StartRegionSandbox` Play에서는 사용자 저장을 건드리지 않고 기존 시험 저장의 `/tmp/eternal-railway-p5-*` 복사본을 사용했다.

1. 이동 중 UI 초안에서 양쪽 역 포트를 반전하고 확정. 실제 경로와 위치는 그대로이고 예약만 생기는지 확인.
2. 예약이 있는 이동 상태를 저장하고 씬을 다시 시작. 시각 필드를 제외한 전체 스냅샷 일치.
3. 다음 첫 역 도착에서 포트/경로 교체, 동일 기차 ID·연료 보존, 중지 요청 유지 확인.
4. 새 예약을 만들고 저장된 취소 버튼의 실제 콜백을 실행. 현재 운행과 노선 버전이 바뀌지 않는지 확인.
5. 실제 Canvas 화면을 확인하고 두 씬의 참조와 31개 콜백을 정적으로 검사.

![예약 변경 대기와 취소 버튼](../../Validation/2026-09-28-railway-pending.png)

3·4역과 회전 검사는 실제 Unity EditMode의 BuildingInstance/노선 코어 테스트다. 실제 맵에서 3·4역을 마우스로 건설한 수동 QA와 동일하지 않다. 전체 UI 입력, 대규모 노선 성능, 연료 용량 축소의 모든 조합은 추가 검증 대상이다.
