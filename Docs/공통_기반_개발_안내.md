# 공통 기반 개발 안내

## 현재 범위

2026-09-14: 전체 개선 계획의 첫 단계인 공통 건물 기반과 독립 검증 씬을 구현했다. 기존 데모 코드는 `Assets/EternalSteam/Code/LegacyDemo`, 세 맵은 `Assets/EternalSteam/Scene/Demo`로 이동했으며 저장 키와 밸런스는 유지한다. 기존 데모 전체의 이전이 완료된 것은 아니다.

공식 문서는 이 저장소의 `Docs`에 둔다. 다운로드 폴더의 기획 원본은 수정하지 않는다. 과거 설계 문서는 당시 제안이며 현재 동작의 근거는 코드·README·실행 안내다.

## 실행

1. Unity 6000.3.14f1에서 `Assets/EternalSteam/Scene/Tests/FoundationSandbox.unity`를 연다.
2. Play → 카탈로그에서 건물 선택 → 설치 → 초록 격자에 여러 건물 배치 → 확정.
3. 임시 건물을 클릭하거나 작업 목록에서 선택해 이동·개별 제거한다. 우클릭/Esc는 작업 전체 취소다.
4. 일반 상태에서 설치된 포탑을 선택하면 방향 설정과 지상/공중/모두 필터가 나타난다. 방향 설정은 마우스로 미리 본 다음 UI의 확정 버튼을 누른다.
5. 회수 → 건물 복수 선택 → 확정. 확정 전에는 실제 기능과 점유가 유지된다.
6. 진행 중인 작업을 확정하거나 취소한 뒤 전투 시작. 결과에서 검증 초기화로 처음 상태로 돌아간다.

첫 씬은 빈 배치에서 시작하며 건물 영구 저장과 보상이 없다. 검증용 적 8개는 지상/공중 각각 4개이고, 모두 처치되거나 30초가 지나 미처리 적이 통과하면 결과로 이동한다. 초록 격자의 중앙 앞쪽에 포탑을 배치하면 기본 전방 부채꼴 안으로 적을 잡기 쉽다.

샘플 에셋을 처음 생성할 때만 `Eternal Steam → Foundation → Create Sample Assets` 메뉴를 사용한다. 기존 샘플 씬이 있으면 덮어쓰지 않는다. 저장된 씬을 연 상태에서 실행해야 한다. 기본 빌드 씬 목록에는 샘플을 추가하지 않아 기존 데모 실행 순서를 유지한다.

## 공통 계약

### 조합과 의존성

- `BuildingDefinition`: 고유 문자열 ID, 표시명, 분류, 점유 크기, 회수 가능 여부, 외형 프리팹, 모듈 목록.
- `BuildingCatalog`: 설치 메뉴에 노출할 정의의 명시적 목록. 분류는 표시 정보이며 기능을 결정하지 않는다.
- `BuildingModuleDefinition.CreateRuntime()`: 건물마다 새로운 `IBuildingModule`을 만든다. 모듈의 공유 에셋을 실행 상태로 사용하지 않는다.
- `BuildingInstance`: 식별자, 위치, 방향, 점유 크기, 모듈 실행 객체. 생성 때 설정을 복사하며 설치된 개체에는 실행 중 에셋 수정이 반영되지 않는다.
- `IBuildingModule`: Initialize → Activate → Tick → Dispose. 생성 중에는 외부 게임 상태를 변경하지 않으며 Activate에서 공격·비용 지불 같은 되돌릴 수 없는 효과를 발생시키지 않는다. 효과 실행은 Tick에서 한다. Dispose는 반복 호출에 안전하고 예외 없이 자체 자원을 해제해야 한다.
- `BuildingServices`: 명시적으로 전달하는 의존성 묶음. 현재는 `ITargetQuery`만 가진다. 공통 런타임은 기존 Horde 타입이나 PlayerPrefs를 참조하지 않는다.
- 생성 실패 시 해당 팩터리가 자신이 생성 중이던 부분 객체를 정리한다. 월드는 반환된 단계별 개체를 정리해 배치 전체를 롤백한다.

처음부터 개별 기능을 독립 UPM 패키지로 나누지 않는다. Runtime/LegacyDemo/Sandbox/Editor/EditModeTests/PlayModeTests 어셈블리를 구분한다. 공통 Runtime은 LegacyDemo와 Sandbox를 참조하지 않는다. 보장하는 제거는 에셋 조합에서 기능을 빼는 작업이다.

### 격자와 작업

- `BuildGrid`는 XZ 정사각 격자. 기준 셀에서 +X/+Z로 양의 정수 크기만큼 점유하고, 외형 중심은 점유 범위 중앙이다. 점유 모양 회전은 없다.
- 실제 점유와 소유자 ID가 있는 임시 예약을 구분한다. 선택은 예약과 독립이다.
- `PlacementSession`은 추가·이동·제거·확정·취소를 제공한다. 이동 실패 시 원래 예약을 유지한다.
- `IPlacementRule`은 요청·전체 작업·격자를 받아 `PlacementResult`를 반환한다. 기본은 지형·점유 검사이고 추가 생성자 인자로 규칙을 연결한다.
- 확정은 전체 재검증 후 비활성 객체 생성 → 등록 → 활성화다. 실패하면 실제 개체·점유를 롤백하고 임시 예약은 유지한다.
- `RecoverySession`은 회수 가능 개체만 선택한다. 확정 전까지 작동과 점유를 유지하며 소실된 대상이 하나라도 있으면 전체를 보류한다. 목록에서 소실 대상을 해제할 수 있다.
- `SandboxSession`은 준비/전투/결과와 일반/설치/회수/방향 작업 모드를 관리한다. 작업이 진행 중이면 전투를 시작하지 못한다.
- `IEditPolicy`의 첫 구현은 `PreparationOnly`. 저수준 월드 API는 정책을 모르는 기반이고, 사용자 명령은 세션의 정책 검사를 거친다.

### 전투

- `ITargetQuery`: 대상 조회와 후보 검색. `TargetHandle`은 ID와 세대 번호로 슬롯 재사용을 구분한다.
- `IDamageReceiver`: 생존 여부와 피해 수신. 적 구현이 이 계약을 제공하므로 공격 기능은 특정 적 클래스를 알 필요가 없다.
- `ITargetSelector`와 `IAttackExecution`을 분리한다. 첫 조합은 `NearestTargetSelector`와 `InstantDamage`다.
- XZ 중심 거리와 부채꼴 판정. 같은 거리면 작은 대상 ID를 우선한다. 사거리와 각도 경계를 포함한다.
- 유효 타겟을 유지하며 사망/범위 이탈/필터 변경 시 재선정한다. 타겟이 바뀌어도 쿨다운을 초기화하지 않는다.
- 공격 간격 단위는 초. 최초 유효 타겟에는 준비된 상태에서 즉시 공격한다.
- 방향 편집은 미리보기만 바꾸며 해당 건물의 Tick을 멈춘다. 확정은 타겟 해제, 취소는 기존 방향 유지다. 현재 사용자는 준비 단계에서만 편집한다.

## 선택 기능과 Inspector 작업

### 기존 동작으로 새 건물 추가

1. Project 창에서 `Create → Eternal Steam → Building`으로 정의를 만든다.
2. 중복되지 않는 ID, 표시명, 점유 크기, 프리팹을 지정한다.
3. `Modules` 목록에 Health 또는 Attack 에셋을 필요한 만큼 조합한다. 같은 모듈 타입은 한 번만 넣는다. 빈 목록도 유효하다.
4. `SampleCatalog.Buildings`에 등록하고 Play 또는 검증 초기화를 한다. UI 코드와 enum 수정은 필요 없다.

공격을 제거하려면 정의의 Modules 목록에서 Attack 참조를 뺀다. 내구도만 있거나 아무 기능도 없어도 배치·선택·회수는 유지된다. 카탈로그에서 항목을 제거하면 다음 세션에서 메뉴에 나타나지 않는다. 이미 실행 중인 개체를 에셋 편집으로 재구성하는 기능은 없다.

### 새로운 기능 작성

`BuildingModuleDefinition`을 상속하고 `CreateRuntime`에서 독립 실행 객체를 반환한다. 새 동작을 작성할 때만 C# 코드가 필요하며 중앙 enum이나 큰 switch에 항목을 추가하지 않는다. 모듈은 다른 모듈을 구체 클래스 전체가 아닌 필요한 인터페이스로 조회할 수 있다. 필요한 외부 의존성이 누락되면 Initialize에서 명시적으로 실패시킨다.

외형 프리팹은 표현용으로 사용한다. 공격 포탑의 선택적 `AttackPivot` 자식은 확정 방향을 따른다. 임시 배치는 게임 스크립트를 실행하지 않는 점유 크기 박스로 표현한다.

Editor Inspector에서 정의·카탈로그 오류를 표시하고 검증 씬의 Play 진입 시에도 검사한다. 중복 ID, 잘못된 크기, 누락 프리팹·모듈, 중복 모듈 타입, 잘못된 공격·체력 수치를 차단한다.

## 검증용 조합과 미정 콘텐츠

| 조합 | 기능 | 목적 |
|---|---|---|
| 기능 없는 건물 | 없음 | 기능 제거와 기본 배치·회수 독립성 |
| 내구도 건물 | Health, 2×1 점유 | 다중 셀과 피해·파괴 |
| 단일 공격 포탑 | Health + Attack | 방향·타겟 유지·필터·즉시 피해 |

검증값은 사거리 18, 부채꼴 90도, 간격 0.5초, 피해 10, 건물 체력 100, 테스트 적 체력 30이다. 제품 밸런스로 확정한 값이 아니다.

자원 생산·설치 비용·넥서스·레벨·시야 차단·이동 장애물·투사체·전투 중 편집·영구 배치 저장은 후속이다. 관련 빈 인터페이스나 동작 없는 버튼을 미리 만들지 않았다. 기존 데모의 연사는 호환 공격 방식으로 보존한 뒤 후속 단계에서 이전한다.

## 테스트 실행

Unity Test Runner에서 `EternalSteam.EditModeTests`와 `EternalSteam.PlayModeTests`를 각각 실행한다. PlayMode 테스트는 검증 씬을 열고 작업을 초기화하므로 플레이 상태를 보존해야 하는 Editor에서는 실행하지 않는다.

```sh
unity command run_tests --mode editor --filter EternalSteam.EditModeTests --filter_type assembly --async_tests true --project-path . --format json
unity command test_status --project-path . --format json
unity command run_tests --mode playmode --filter EternalSteam.PlayModeTests --filter_type assembly --async_tests true --project-path . --format json
```

CLI 연결이 없는 CI에서는 Unity Test Runner의 batchmode `-runTests -testPlatform EditMode`와 `PlayMode`를 사용한다. 검증 씬은 저장소에 포함되어 있어 테스트 전에 생성 메뉴를 실행할 필요가 없다.

### 기존 검증 도구 구분

| 도구 | 용도 / 상태 |
|---|---|
| `VerifyFoundationRegression.cs` | 현재 세 맵의 로비·출격·클리어·패배·재도전·보상·저장. 별도 테스트 키 사용 |
| `VerifyPrototypeLoop.cs` | 현재 피해·관통·로비·보상·저장 UI 흐름 |
| `VerifyStages.cs` | 현재 1500/3000/5000 고정 수량·통과 처리·다음 단계 |
| `VerifyCapacityUpgrade.cs` | 현재 설치 한도 구매·저장·풀보다 큰 스테이지 |
| `VerifyGridOccupancy.cs`, `VerifyBuildSurfaces.cs` | 기존 데모의 배치 외형·격자 회귀용. 새 공통 격자 테스트와 별개 |
| `VerifyHordeHud.cs`, `VerifyAutomaticFire.cs`, `VerifyDirectionalHorde.cs`, `VerifyTowerRoles.cs`, `VerifyHordeDemo.cs` | 이전 UI·즉사·연사·무한 출현 가정이 포함될 수 있는 역사적 도구. 현재 전체 기능의 합격 기준으로 사용하지 않음 |
| `CreateHordeDemo.cs`, `CreateHordeMaps.cs` | 초기 씬 생성 도구 |
| `ProbeHordeFlow.cs` | 수동 흐름 진단 |

```sh
unity command run_script --file Tools/VerifyFoundationRegression.cs --entry VerifyFoundationRegression.Main --timeout_ms 60000 --project-path . --format json
```

회귀 도구는 Play 중에만 실행하며 장면을 바꾸고 전투를 초기화한다. 새 기반 테스트는 기존 저장 키를 사용하지 않는다.

## 이후 이전 순서

1. 완료: 독립 공통 기반과 검증 씬.
2. 기존 데모의 배치와 표현을 공통 건물에 연결. 기존 설치 조작은 어댑터로 유지.
3. 기존 전투·적 관리·인스턴싱 분리. 배열·공간 조회·슬롯 재사용을 유지하고 기존 4종 공격을 호환 실행 방식으로 옮김.
4. 맵·스테이지·포탑을 카탈로그로 이전하고 고정 UI 개수 제거.
5. 진행·보상을 별도 서비스로 이전. enum 순서를 고정 ID에 매핑하고 기존 저장 키는 성공적인 버전 이전 전까지 보존. 삭제 콘텐츠 기록도 보존.
6. 도구·문서·빌드 절차 정리와 콘텐츠 구현.

성능 판정은 3단계 전투 이전 때 동일 장비·시드·배치·4,000 동시 적 부하에서 3회 비교한다. CPU 프레임 시간 중앙값·95백분위와 GC 할당을 기록하고 반복되는 10% 초과 악화 또는 새 상시 전투 GC 할당을 해결한다. 첫 단계 검증 씬의 단순 TargetRegistry는 대규모 적 최적화 구현이 아니다. 이번 단계에서는 기존 전투 코드를 바꾸지 않았으므로 성능 개선이나 이전 전후 성능 동등성을 주장하지 않는다.


폴더 소유권과 신규 파일 배치 기준은 [폴더 구조](폴더_구조.md)를 따른다.
